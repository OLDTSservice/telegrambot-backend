Telegram 機器人後台管理系統 — 功能說明文件

涵蓋機器人判斷機制、條件限制、以及網頁後台每個頁面的按鍵功能。內容依據目前程式碼實際邏輯整理。

技術架構：FastAPI（後端）＋ React / Ant Design（前端）＋ SQLite（資料庫）＋ python-telegram-bot（輪詢接收訊息）＋ Claude Haiku（知識庫問答 AI）

系統架構總覽

本系統是一套可同時管理「多個 Telegram 機器人」的後台，每個機器人各自獨立運作、各自綁定關鍵字規則與知識庫。除了 Telegram，系統也另外支援 Microsoft Teams 機器人模組（架構相同、頁面獨立），本文件僅聚焦於 Telegram 機器人 相關功能。

運作方式

  • 每個機器人啟用後，後端會用 python-telegram-bot 以獨立執行緒對 Telegram 伺服器進行 長輪詢（polling），收到訊息就丟進判斷流程。
  • 所有規則、知識庫內容、對話記錄都存在同一個 SQLite 資料庫，公司與家裡的本地資料庫各自獨立，只有部署在 Render 上的雲端版本才是實際對外運作的機器人。
  • 知識庫問答由 Anthropic Claude（claude-haiku-4-5）負責，机器人不會憑空回答，只會根據知識庫內容作答。

帳號與權限

後台登入採帳號密碼＋JWT Token，Token 有效期 24 小時。共分三種角色：

角色可檢視可新增／編輯／切換開關可刪除可管理帳號（人員）
superadmin 超級管理員✅✅✅✅
editor 編輯員✅✅✅❌
viewer 檢視者✅❌（按鈕會反灰）❌❌
預設帳號 系統初次啟動會自動建立一組 superadmin 帳號 admin / admin123，建議上線後盡快至「帳號管理」頁面更改密碼或新增正式帳號。

機器人管理頁面

側邊選單：Telegram 機器人 → 機器人管理

此頁分為四個分頁（Tab）：機器人管理、群組管理、AI機器人救援、Notify管理。

機器人管理 Tab

管理所有已串接的 Telegram Bot（一個 Bot Token 對應一個機器人身份）。

按鍵 / 欄位功能說明
新增機器人輸入名稱與從 @BotFather 取得的 Token，建立後立即啟動輪詢（polling）開始接收訊息。Token 不可與現有機器人重複。
啟用開關（Switch）關閉時會呼叫 stop_bot() 停止該機器人的 Telegram 輪詢執行緒；重新開啟則呼叫 start_bot() 重新連線。停用中的機器人完全不會收到／處理任何訊息。
編輯（鉛筆圖示）修改機器人名稱或 Token。
刪除（垃圾桶圖示）停止該機器人並自資料庫移除；連動的規則、知識庫文件、對話紀錄需另外處理（不會自動一併刪除）。有二次確認彈窗。
Token 欄位顯示畫面上僅顯示前 20 碼並以 … 省略，避免明碼外洩。
JILI遊戲素材查詢 開關 開啟後，訊息含「素材/material/asset/icon/圖示/圖標/入口圖」等關鍵字時，會串接同事提供的 JILI Game Search API， 從訊息中比對出遊戲名稱（支援英/繁中/簡中，一則訊息可同時問多款），呼叫 API 取得 Google Drive 的 Icon／Material 連結並回覆廠商。 訊息中獨立出現的純數字（如 109）視為 Game ID，直接在本地清單做精確比對，不經 AI 猜測。 找不到遊戲或查無資料時不會中斷，會改走一般知識庫查詢流程。
TADA遊戲素材查詢 開關 與「JILI遊戲素材查詢」邏輯完全相同，只是串接 TADA Game Search API（不同網址），且 TADA 遊戲清單只有英文名稱、無中文。 兩個開關各自獨立，一個機器人通常只服務單一廠商，只會開啟其中一個。
TADA Gamelist進階查詢 開關 預設關閉，僅供 TADA 機器人使用。開啟後可處理三種問法：
1. 熱門遊戲排行（如「top 10 games」「熱門遊戲」）：未指定地區時回覆 GameRank 總表連結；有指定國家/市場時（依內建對照表換算成大區域，如沙烏地→West Asia）回覆該區域 Overall 排行，並誠實註明是「合併整個地區」的數據。
2. 單一遊戲欄位查詢（如「GameID 775 的 min bet 是多少？」）：需同時包含「遊戲識別（名稱或GameID）」與「欄位關鍵字」才會觸發，缺一律視為條件不足。
3. 複合條件篩選（如「有哪些 Med 波動度的 Slot game？」）：篩選 Game List 全表，只示意列出前 5 筆結果並附總表連結，不會把全部符合結果都列出來。
三種情況若判斷「問題不完整」（例如只講欄位沒講遊戲）則不猜、不觸發自動回覆，直接轉人工；但訊息本身低於 10 字元時，比照其他功能一律視為雜訊完全略過（不回覆、不記錄）。 AI 只負責從訊息判斷使用者的意圖（是哪個市場/遊戲/欄位/篩選條件），實際查表比對皆由程式碼精確處理，不讓 AI 直接讀表回答數字，避免結構化資料被誤答。
遊戲素材查詢的資料來源 兩個 API 皆由同事的 TADA Gaming 技術團隊提供、每日 09:36（GMT+8）自動更新資料，無需 API Key。本系統會將完整遊戲清單快取 24 小時，減少重複呼叫。
TADA Gamelist進階查詢的資料來源 資料來自 TaDa Game List 2026 這份 Google Sheet 的 GameRank／Game List 兩個分頁（透過公開 CSV 匯出網址讀取，無需 API Key），同樣快取 24 小時。國家/幣別對應大區域的內建對照表目前僅涵蓋已知範例（如 West Asia），遇到新市場需另外補充對照表才能正確辨識。
機器人「運行中」標籤 列表上的綠色「運行中」標籤只代表資料庫 is_enabled=true，若要確認實際輪詢是否存活，需透過 GET /api/bots/{bot_id}/status 或直接觀察是否有訊息進來；若 Token 失效或網路異常，輪詢執行緒可能啟動失敗但畫面仍顯示已啟用。此時可用「重新啟動」（API 提供、目前前端未顯示對應按鈕）排解。

群組管理 Tab

列出指定機器人「曾經收到訊息」的所有 Telegram 群組／聊天室，並可個別控制每個群組的 AI 問答及白名單廠商驗證設定。

按鍵 / 欄位功能說明
選擇機器人（下拉選單）先選機器人才會載入其群組清單。
搜尋群組名稱依群組名稱關鍵字篩選。
AI 問答 開關此開關直接對應 TelegramGroupSetting.ai_enabled（預設為開啟）。關閉後，該群組的訊息完全不會查詢知識庫，機器人只剩「關鍵字規則」仍會作用；此設定也是觸發「AI 救援」的先決條件之一，詳見 訊息流程 — 群組 AI 開關。
群組類型標籤私聊 / 群組 / 超級群組 / 頻道，取自 Telegram 原生 chat.type。
即時對話管控 開關 此為群組層級的管控開關，可讓特定群組單獨進入管控模式，而不影響其他群組。判斷邏輯採 OR 規則：
• 若「即時對話管控頁面」的機器人總開關已開啟 → 所有群組都進入管控模式（無視此欄設定）
• 若機器人總開關關閉，但此欄開啟 → 僅此群組進入管控模式，其他群組仍自動回覆
• 兩者皆關閉 → 完全一般模式，全部自動回覆
詳見 即時對話管控頁面 與 訊息流程步驟 5。
白名單廠商驗證 欄（Tag + 🛡 按鈕） 顯示該群組廠商驗證功能的狀態（「已啟用」藍色標籤 / 「未啟用」灰色標籤）。點擊盾牌圖示按鈕開啟設定 Modal，可設定：
  • 廠商驗證開關：開啟後，此群組的白名單申請在執行前會先驗證廠商是否在允許清單內，不符合則靜默拒絕。
  • 允許廠商前綴（逗號分隔，不分大小寫）：填入廠商名稱或前綴。比對採分隔符號感知模式——前綴 P 僅允許廠商名稱完全等於 P、或以 P_（底線）、P-（破折號）開頭；不會誤放行恰好含同樣字母但屬不同廠商的名稱（例如填 ON9 只允許 ON9、ON9_sub，不會放行 On9gaming）。填 TitanTR1 則允許 TitanTR1、TitanTR1_SCFLY 等旗下子品牌。
未填允許前綴或關閉開關時，此群組不受廠商限制，任何廠商都可加白。
自動建立工單 開關 對應 TelegramGroupSetting.ticket_creation_enabled（預設開啟）。關閉後，此群組所有「一般模式下自動送出」的成功回覆 （關鍵字規則命中、知識庫回答成功、白名單加白成功、JILI/TADA遊戲素材查詢成功、管控模式人工發送）一律不建立 Freshdesk 工單，該群組的回覆內容不受影響、照常發送。 由於 Notify 通知是掛在「工單建立完成後」才觸發，關閉此開關等同該群組完全不會有任何 Notify 通知。
廠商驗證開關預設關閉 新加入的群組預設不啟用廠商驗證，若需要限制特定群組只能提交特定廠商的白名單申請，需手動到此頁面設定，避免遺漏。

AI機器人救援 Tab

逐機器人設定「AI 救援」功能的啟用與逾時時間，詳細運作機制見 AI機器人救援（運作細節）。

按鍵 / 欄位功能說明 / 限制
啟用救援 開關開啟後：若群組 AI 問答已關閉，且該群組最後一則訊息逾時仍未被人工「引用回覆」，AI 會自動判斷是否為問題並接手回覆一次。
逾時時間（分鐘）可調整範圍 1 ～ 1440 分鐘；只有啟用救援時此欄位才可編輯。
狀態標籤顯示「未啟用」或「監控中（N 分）」。

Notify管理 Tab

設定「Freshdesk 工單建立通知」的接收機器人與目標群組。每當機器人在一般模式下自動回覆（關鍵字規則、知識庫問答、白名單成功處理），背景執行緒會嘗試建立 Freshdesk 工單；不論建立成功或失敗，都可透過此設定讓指定機器人自動把結果通知到指定的 Telegram 群組。

按鍵 / 欄位功能說明 / 限制
通知開關關閉時完全不發送任何工單通知；開啟後，每筆 Freshdesk 建單動作（成功或失敗）都會觸發一則通知訊息。
發送通知的機器人選擇用哪一個 Telegram 機器人來傳送通知訊息；需先在「機器人管理 Tab」建立並啟用機器人後才會出現於此下拉選單。
通知目標群組選擇要把通知發到哪個群組；下拉選單來源為所選機器人曾有訊息活動的群組清單（若目標群組不在列，需先讓機器人在該群組收到至少一則訊息）。選定後會顯示群組 ID 供確認。
儲存設定儲存後立即生效，下次工單建立時即會發送通知到新設定的目標。
全域單一設定 Notify 設定是整個系統共用一組，不區分機器人——所有機器人的 Freshdesk 工單通知都會發到同一個目標群組。若需要按機器人分開通知，目前需手動更換設定。

通知訊息格式

工單建立成功時：
群組名稱：（觸發回覆的 Telegram 群組名稱）
問題訊息：（觸發開單的原始問題內容）
回覆內容：（機器人實際回覆給使用者的內容）
建立狀態：✅ 成功
工單編號：#12345
工單建立失敗時：
群組名稱：（觸發回覆的 Telegram 群組名稱）
問題訊息：（觸發開單的原始問題內容）
回覆內容：（機器人實際回覆給使用者的內容）
建立狀態：❌ 失敗
失敗原因：HTTP 500: Internal Server Error

「問題訊息」欄位是為了在同一群組短時間內有多筆提問時，方便對照失敗通知究竟對應哪一則問題；「回覆內容」欄位則是機器人當下實際送出的文字（例如關鍵字規則的固定回覆、知識庫查詢到的答案，或白名單處理成功時的 Done），方便在通知群組直接核對回覆是否恰當，不需要再回頭查對話紀錄。

通知不觸發的情境 管控模式下由人工手動發送的回覆、Fallback 無解答回覆、以及 AI 救援回覆，都不會建立 Freshdesk 工單，因此也不會觸發 Notify 通知，詳見 訊息處理總流程。

訊息處理總流程（機器人判斷機制）⭐

這是整個系統最核心的邏輯：機器人每收到一則文字訊息，會依序通過以下判斷關卡，只要中途符合任一條件就會直接結束（return），不會繼續往下判斷。以下按實際程式碼執行順序說明。

0
忽略名單檢查
比對發送者的 user_id 或 @username（不分大小寫）是否命中該機器人「忽略名單」中已啟用的項目。 若該筆忽略設定有填「例外關鍵字」，且訊息內容包含其中任一關鍵字（逗號分隔可填多個，不分大小寫），則視為未命中，該則訊息照常往下處理。
命中且無例外關鍵字符合 直接結束，完全不回覆、不留任何統計或對話紀錄
未命中，或命中但訊息含例外關鍵字 繼續下一步
0.5
後台白名單自動處理（僅該機器人開啟此功能時執行）
先檢查訊息是否符合「申請表單格式」（≥3 行「數字編號＋冒號欄位」，例如結構化的 AGENT 開戶申請單）——若是，直接跳過白名單流程，交給後續的申請表單偵測處理，避免把表單裡的欄位值（如 Brand Name、Environment、Wallet Type 等）誤當成代理帳號逐一嘗試比對廠商。非表單格式的訊息，才繼續偵測是否為「後台 IP 加白」請求（關鍵字＋IP 格式皆符合），符合則自動登入內部白名單管理系統執行加白，詳見 後台白名單處理頁面。
至少一組帳號成功 回覆固定文字 Done，並背景建立 Freshdesk 工單
廠商驗證不通過 解析出的廠商名稱不在此群組的允許清單內 → 不執行加白、不建工單；依訊息語言回覆固定訊息（中文：「您好，人員將會協助確認，請稍後」／英文：「Hello, our team will assist you shortly. Please wait.」），詳見 群組管理 Tab
全部失敗 / 無法解析 靜默不回覆、不建工單
符合申請表單格式 完全不進入白名單流程，直接交由 申請表單偵測 處理（回覆制式等待訊息，記錄為無解答對話）

⚠️ 此步驟不受「即時對話管控模式」影響——即使該機器人開啟了管控模式，只要訊息符合白名單請求格式，機器人仍會自動處理並直接回覆，不會進入待審佇列。

為什麼要先排除申請表單格式 早期版本沒有這層排除，曾發生過結構化的「AGENT 開戶申請單」（含 Brand Name、Domain URL、Environment、Wallet Type 等多個編號欄位，其中一欄剛好也提到 Backoffice IP）被誤判為白名單請求，程式把表單裡每個欄位的值（例如 CreditKhmer168、Transfer、Production）都當成候選代理帳號，逐一登入後台系統比對真實廠商清單（每次比對都要重新登入＋下載完整廠商清單，相當耗費資源），且若某個誤比對到的廠商剛好也在該群組的允許清單內，會導致加錯廠商的白名單。加上這層排除後，凡符合申請表單格式的訊息一律不進入白名單流程。
1
關鍵字規則比對
依序檢查該機器人所有「已啟用」的關鍵字規則，只要訊息文字（不分大小寫）包含某條規則的關鍵字即算命中（取第一條符合的規則，不會同時觸發多條）。

雙語回覆判斷：命中後，系統會檢查提問是否含有中文字元（CJK 字符範圍）：
• 提問含中文 → 使用「中文回覆」
• 提問純英文 + 該規則有填「英文回覆」 → 使用英文版本
• 提問純英文 + 未填英文回覆 → 仍使用中文回覆（不會空白）

管控模式開啟 記錄訊息 + 建立「待發送回覆」（已套用語言判斷），等待人工於即時對話頁面確認發送
一般模式 直接回覆（對應語言版本）＋記錄群組統計＋背景建立 Freshdesk 工單

Fallback（無解答）與冷卻機制
僅在「一般模式」且知識庫無答案時觸發。以「機器人＋發送者（或聊天室）」為單位設有 10 秒冷卻：距離該使用者「上一次真正送出 Fallback 回覆」不到 10 秒，再次觸發會被直接忽略（不回覆、不記錄），避免使用者連續發訊息時被機器人洗版式回覆。此冷卻是滾動窗口（以「上次實際回覆的時間點」為基準），不是「固定次數」——若兩次觸發間隔剛好超過 10 秒，兩次都會各自收到回覆並各自重新計時。
冷卻只影響「無解答」的 Fallback 訊息：若冷卻期間使用者提出的是知識庫能夠回答的新問題，機器人仍會正常查詢並回覆，不受此冷卻限制——冷卻判斷發生在「知識庫查無答案」的分支裡，知識庫有答案時走的是完全不同的程式碼路徑，兩者互不影響。

1訊息中至少 3 行符合「數字編號＋句點/頓號＋內容＋冒號＋內容」格式（例：1. 商戶名字：ABC）。
2訊息開頭含固定的客服工單範本開場白（Please provide the list below／可以提供以下资料以便查询），即使欄位沒有數字編號也判定為表單。
3同時含「遊戲」欄位標籤（游戏名称/Game：）與「帳號」欄位標籤（代理账号/Username：等），且訊息中沒有 IP 位址——白名單請求也常見這種欄位組合，但一定會附上要加白的 IP，用「有沒有 IP」區分兩者，避免誤擋真正的白名單請求。
4多行「標籤：值」格式但沒有數字編號（例如 API 串接申請單常見的 Brand Name／Website URL／Callback URL 等欄位），至少 4 行才視為表單，且訊息中不能含白名單相關字樣（白名单／白名單／whitelist／加白），避免誤擋白名單請求。單獨一行的網址（https://... 開頭）不算欄位標籤——網址本身的協定冒號（https:）曾被誤判成「標籤：值」格式，導致「網址＋USER＋PW＋IP」這種沒有寫明白名單字樣的訊息被誤判成表單、連帶擋住白名單自動處理。
icon／material／rtp 沒指定遊戲時的例外 TADA Gamelist進階查詢判斷「單一遊戲欄位查詢」條件不足（有欄位、沒指定遊戲）時，預設會直接轉人工；但 icon／material／rtp 這三個欄位額外設有例外——若知識庫裡已補上「沒有指定遊戲時」的通用問答（例如統一的素材資料夾連結），會改為放行給知識庫查詢，而不是直接轉人工。其餘欄位（如 min bet、volatility）沒有這個例外，沒指定遊戲時仍一律轉人工，因為這些欄位沒有指定遊戲就沒有意義的通用答案。

純問候／感謝／道別語、含「ignore」字樣、純TAG帳號（_is_greeting_or_thanks() / _contains_ignore_keyword() / _is_mention_only_message()）

這三個判斷命中後都是直接結束、不回覆、不記錄（與其他機制會回覆制式訊息不同）：

  • 純問候／感謝／道別語：訊息去除標點符號與大小寫後，若整句完全等於清單中的問候／感謝／道別語才算命中（不是包含，是整句相符），避免像「Hi Team, would like to ask...」這種開頭是問候語、但後面有實際問題內容的訊息被誤擋。
  • 含「ignore」字樣：訊息中只要出現「ignore」這個字（不分大小寫、不限完整一句、可包含在其他文字中），就直接略過。與上面「整句完全相符」不同，這條是子字串比對——即使訊息裡還夾雜其他文字（例如「sorry ignore my last message, but can you help check the RTP」），整則訊息仍會被略過，不會另外處理後面的問題。此為刻意的設計取捨：這類訊息絕大多數情況下確實不需要處理，極少數例外由人員自行查看群組對話即可，不需要機器人額外攔截處理。
  • 純TAG帳號：訊息去除頭尾空白後，切成一個個 token，若每一個 token 都符合 @帳號 格式（英數字與底線），就判定為純TAG訊息，不限定特定帳號、tag 幾個都算，例如 @OLDTS_service 或 @OLDTS_service @JiliSerivceprodbot @fh2980112。若訊息除了 tag 還有其他實際文字內容（例如「@OLDTS_service 請問這個問題...」），則不受影響，仍正常走後續流程。

此功能用於自動化處理群組內常見的「後台 IP 加白名單」請求，省去人工登入內部系統手動新增的步驟。

自動偵測與比對規則

整體流程分成四大階段，由上而下依序判斷：① 排除表單 → ② 判斷是否為白名單請求 → ③ 解析帳號 → ④ 比對廠商。

① 申請表單格式排除（最優先）

訊息若符合「申請表單格式」（≥3 行「數字編號＋冒號欄位」，例如結構化的 AGENT 開戶申請單）， 一律不進入白名單偵測與比對，即使訊息裡也提到後台/白名單/IP 相關字樣，避免表單欄位值被誤當成代理帳號逐一嘗試比對廠商。 此檢查在下方「② 觸發關鍵字」判斷之前執行。

② 觸發關鍵字（判斷是否為白名單請求）

符合以下任一規則、且訊息中同時含有至少一個 IPv4 位址，才會被視為白名單請求：

規則判斷方式
規則一
連續詞組比對		 訊息需包含連續字串，例如 whitelist bo ip、bo ip、backend ip、加白后台ip、加白后台、後台ip、加白後台、whitelist backend、backoffice ip、backoffice whitelist、后台過白、后台过白、後台白名單 等。
規則二
三詞共現比對（較寬鬆）		 若規則一未命中，改檢查訊息中是否各自出現（不需相鄰、不需連續）「白名單類字樣」（白名單／白名单／whitelist／加白）與「後台類字樣」（後台／后台／backend／backoffice／kiosk／獨立出現的縮寫 bo）。
用於涵蓋像「商戶：xxx／環境：正式／類型：後台／IP：1.2.3.4」這種欄位式格式（關鍵字分散在不同欄位、不是連續字串，規則一比對不到）。
bo 縮寫採單字邊界比對，不會誤判 about／box／labor 等字。
問句排除訊息含「怎麼」「如何」「請問」「how to」等疑問語意詞彙、或整句結尾是「？」「?」時不觸發此規則，避免把單純詢問流程的訊息誤判成提交申請。結尾判斷「？」「?」符號本身只有出現在整句結尾才算疑問句，句子中間出現的孤立問號（例如格式誤植的 IPv4: ? 1.2.3.4）不會觸發問句排除，避免把這類訊息誤判成疑問句而漏接。此排除僅套用於規則二／規則四，規則一（含「後台白名單」等連續詞組）沒有問句排除，例如「請問如何加到後台白名單？」仍會被規則一直接命中。
規則三
內部網址比對（選用）		 訊息若包含環境變數 WHITELIST_ADMIN_DOMAINS 設定的內部後台系統網址（逗號分隔可設定多個），即視為請求，不需額外出現「白名單」字樣，但仍會排除問句型態。此環境變數預設未設定，未設定時規則三完全不啟用。
規則四
帳號標籤格式比對（選用，群組獨立開關）		 訊息含「白名單/whitelist」字樣 + 「標籤：帳號」格式的行（例如 Jili : JK481A_MYR，不限定標籤詞）， 即使完全沒提「後台」兩個字也視為請求；仍會排除問句型態與 API 排除字樣。
用於涵蓋廠商只說「whitelist IP」卻沒特別強調「後台」的口語化請求（例如「tolong whitelist IP」）。
此規則預設不啟用，需在「群組管理 Tab」個別開啟「Bo白名單添加放寬」開關才會對該群組生效，其餘群組不受影響。
排除規則（優先權高於以上三條規則） 若訊息中出現 api ip、api whitelist、加白api 等「API IP」相關字樣，一律視為非本功能處理範圍，即使同時滿足規則一、二、三、四也不會觸發。

③ 帳號與廠商解析

優先從訊息中擷取 Username / 帳號 / 后台账号 / 商户 / 商戶 / ID 等標籤後方的帳號字串； 標籤後方若以逗號（全形，或半形,）列出多個帳號，會全部個別解析 （例如 商户： SEA_NYG88_INR， SEA_NYG88_INR_SUB 會拆成兩組帳號分別比對廠商）。 訊息裡若有多個獨立標籤區塊（例如同一則訊息複製貼上兩段申請格式，各自都有一行 代理账号/Username：xxx）， 會掃描出所有符合標籤格式的地方，不會只取第一個。
若訊息沒有任何標籤， 改為逐行掃描，取「單獨一行、格式像帳號（英數字＋底線／破折號，無空白）」的行當作帳號 （例如 Ogpro_SS9AU_MYR 單獨成行，前面沒有 Username: 之類文字，一樣抓得到）； 但單獨成行時必須含底線／破折號（多段格式）才會被當作帳號，只有單一詞彙的行（例如訊息開頭單獨一行的品牌／遊戲名稱 JILI）不會被誤判成帳號。
若該行是「標籤 + 冒號 + 帳號」格式，只要符合以下任一條件即會解析：① 標籤與 Username/User/ID/帳號 等詞夠相近（文字相似度比對，容許 USWER:、Usre: 等少量手誤）； ② 標籤即使完全不相關（如任意品牌代碼 GMSJE:），但冒號後的值本身是多段格式 （含底線／破折號，例如 Con99_VCEM_MYR），因為真實帳號幾乎都是多段組成。 兩者皆不符合時（例如 Product : Jili，標籤不相關且值只是單一詞彙）才不會被誤判為帳號。
掃描時若某行含 IP，只跳過該行、不會中止整體掃描，因為帳號清單有時會排在 IP 後面才列出； 單獨成行的常見客套結尾字樣（如 Thanks、Regards）會被排除，不會誤判為帳號。
取得帳號後以底線／破折號拆解各段；一則訊息可能包含多組帳號（多行列出），會逐一嘗試比對廠商。

④ 廠商比對（六層漸進式演算法）

登入內部白名單管理後台取得完整廠商清單後，依序嘗試下列步驟，一旦唯一確認廠商即停止：

提前消歧：群組允許清單優先於任何猜測性 fallback Step 4a、4b、4c、4c-2、4c-3 任一步驟若剛好找到多筆候選、無法自動唯一判定時， 只要此群組已在「群組管理 Tab」開啟廠商驗證並設定允許清單，會優先用該清單篩選候選——若篩選後剛好只剩一筆即直接採用， 不必等到 Step 4d 才判斷。只有在群組允許清單無法篩出唯一結果時（清單未設定、或篩選後仍有多筆），才會退而使用 Transfer/Seamless 段數猜測等其他 fallback 策略； 猜測結果依然中止則維持原本「安全中止不猜測」的行為。此優先順序確保「群組管理員的明確設定」永遠比「依命名慣例的猜測」更權威， 避免猜測結果與群組實際允許的廠商衝突（衝突時猜測可能被 Step 4d 誤擋，或在群組未設定驗證時猜錯而無安全網攔截）。
步驟判斷方式
Step 4a
前綴逐層比對		 從帳號第一段開始，每次多加一段組成前綴，篩選廠商名稱等於或以該前綴為起頭的清單。若某層剛好只剩一筆即命中；若某層結果為 0 筆，嘗試用上一層候選清單再做 fallback（回推帳號完整名是否以候選廠商名稱為起頭），唯一則命中。

Transfer / Seamless 段數猜測（最後 fallback）若某層剛好找到 2 筆候選，且兩者恰好是同一品牌前綴下的 {品牌}_Transfer 與 {品牌}_Seamless 兩條線：先嘗試用群組允許清單消歧（見上方提示），若清單無法篩出唯一結果，才依帳號段數猜測：共 3 段（品牌_子代理_幣別，如 Con99_XXX_MYR）判定為 Transfer；共 2 段（品牌_子代理，如 Con99_XXX）判定為 Seamless。此為多數廠商通用命名慣例，屬於猜測性質，僅在群組允許清單無法提供更明確依據時才會使用；段數不符或候選非此組合則不套用，繼續原本逐層比對流程。
Step 4b
第一段前綴反向比對		 若 4a 仍未確定，改以帳號第一段為基準，尋找廠商名稱是該第一段前綴的所有廠商（即廠商名 ⊆ 帳號第一段），取名稱最長且唯一者。
Step 4c
段落成員比對		 若 4b 仍未確定，將所有廠商名稱以底線／破折號拆成多段，找出其中任一段等於帳號第一段的廠商。例如帳號 SCFLY_spinpokies29_MYR 第一段 SCFLY 是廠商 TitanTR1_SCFLY 的第二段，此步驟即可命中；取最長且唯一者。
Step 4c-2
廠商名稱後綴比對		 若 4c 仍未確定，改判斷帳號第一段是否為某個廠商名稱的結尾（廠商名稱與帳號第一段之間沒有底線／破折號分隔，前面幾個 Step 因此都比對不到）。例如帳號 TR1_EZBet77_MYR 第一段 TR1 剛好是廠商 TitanTR1 的結尾（Titan + TR1 中間無分隔符號），此步驟即可命中；唯一命中才算數，找到多個候選則安全中止不猜測。
Step 4c-3
廠商名稱前綴比對		 若 4c-2 仍未確定，改判斷帳號第一段是否為某個廠商名稱的開頭（廠商名稱與帳號第一段之間沒有底線／破折號分隔，是 4c-2 的鏡像方向）。例如帳號 HWTYBMSTR_hwtyb0037_MYR 第一段 HWTYBMSTR 剛好是廠商 HWTYBMSTRMYR 的開頭（HWTYBMSTR + MYR 中間無分隔符號）。取候選中名稱最短且唯一者——因為帳號第一段有時同時是多個廠商名稱的前綴子集（例如 HWTYBMSTR 同時是 HWTYBMSTRMYR 與 HWTYBMSTR1to1MYR 的開頭），取最短、最貼近帳號原字串的那筆才是正確答案；仍有多筆同長度候選則安全中止不猜測。
Step 4d
群組廠商驗證		 確認廠商後，若此群組已在「群組管理 Tab」開啟廠商驗證並填有允許前綴，則判斷解析到的廠商名稱是否以允許前綴之一開頭；不符合則視為本群組無權提交該廠商的加白申請，靜默拒絕（詳見下方「群組廠商驗證」說明）。
解析成功 ≥1 組帳號 呼叫內部系統新增白名單 IP，機器人回覆 Done，並建立 Freshdesk 工單留存紀錄
廠商驗證不通過（Step 4d） 解析到的廠商不屬於此群組的允許廠商 → 不加白、不建工單；依訊息語言自動回覆固定訊息（中文：「您好，人員將會協助確認，請稍後」／英文：「Hello, our team will assist you shortly. Please wait.」）
全部失敗（廠商無法判斷 / 登入失敗等） 機器人不回覆任何訊息，避免誤導使用者以為已處理完成；僅在記錄檔中留下失敗 log

群組廠商驗證（Step 4d）

為防止不同群組的代理將加白請求送到錯誤群組（例如 B 廠商代理在 A 廠商群組發送申請），每個群組可獨立設定「允許廠商前綴」白名單：

欄位說明
廠商驗證開關 預設關閉（不限制）。開啟後，系統在完成廠商比對（Steps 4a–4c-3）後會執行前綴驗證，不符合則靜默拒絕整筆請求。
允許廠商前綴（逗號分隔） 填入允許的廠商名稱或前綴，不分大小寫。採分隔符號感知比對，前綴 P 通過條件為以下三者之一：
• 廠商名稱 完全等於 P
• 廠商名稱以 P_（底線）開頭
• 廠商名稱以 P-（破折號）開頭

範例：
• 填 ON9 → 允許 ON9、ON9_subagent，但不放行 On9gaming（屬於不同廠商，名稱中間無分隔符號）
• 填 TitanTR1 → 允許 TitanTR1、TitanTR1_SCFLY 等旗下子品牌
• 留空（或關閉開關） → 不做任何限制，任何廠商皆可加白
設定入口：群組管理 Tab → 找到目標群組 → 點擊「🛡」按鈕 → 開啟「廠商驗證」開關並填入允許前綴後儲存。每個群組可設定不同的允許清單，互不影響。

單一總代理模式（訊息無帳號時的廠商判斷）

部分廠商提交白名單申請時，訊息只包含「後台關鍵字＋IP」，沒有任何代理帳號（例如轉發自其他系統的固定格式通知）。 此情況下，原本的帳號解析邏輯（Step 4a–4c）完全無帳號可比對，會直接判定失敗。若某群組確定只服務單一總代理， 可開啟「單一總代理模式」，讓程式在偵測不到帳號時，直接以此群組設定的總代理名稱精確比對後台廠商清單並加白。

欄位說明
單一總代理開關 預設關閉。開啟後，僅在該訊息解析不到任何帳號（但符合後台關鍵字＋IP 格式）時介入；訊息本身若有帳號，仍優先走原本的帳號解析流程，不受此設定影響。
總代理名稱 需與後台系統中的廠商名稱完全一致（忽略大小寫），例如 gamius。比對方式為精確比對，不做前綴或子字串比對；若後台系統找不到完全符合的廠商名稱，視為失敗，機器人不回覆、僅記錄失敗 log。
設定入口：群組管理 Tab → 找到目標群組 → 點擊「🪪」按鈕 → 開啟「單一總代理」開關並填入總代理名稱後儲存。
與「廠商驗證」的關係 兩者可同時開啟、互不衝突：「單一總代理」只在訊息無帳號時介入判斷廠商；「廠商驗證」則是在廠商確定後（不論來自帳號解析或單一總代理設定）再檢查是否為此群組允許的廠商。
與寬鬆觸發規則（規則二）疊加的風險 若某群組同時開啟「單一總代理模式」，且訊息被觸發規則二（三詞共現）誤判為白名單請求、又剛好沒解析到帳號，系統會直接以該群組設定的總代理名稱真的執行加白，而非像未開啟單一總代理模式的群組那樣靜默失敗、繼續走正常問答流程。換句話說，「單一總代理模式」是唯一會把「觸發規則誤判」從「無傷害的靜默失敗」放大成「真的寫入後台系統」的地方，替這類群組開啟此模式時請特別留意。

Bo白名單添加放寬（規則四開關）

每個群組可獨立開啟「規則四」：訊息只要含「白名單/whitelist」字樣 + IP + 「標籤：帳號」格式的行， 即使完全沒提「後台」兩個字也視為請求。適用於多數廠商提供資訊都齊全、但少部分只講「whitelist IP」沒特別強調「後台」的情境。

欄位說明

設定入口：群組管理 Tab → 找到目標群組 →「Bo白名單添加放寬」欄位直接切換開關，無需額外彈窗設定。
放寬後的風險 規則四不要求「後台」字樣，只要訊息含白名單/whitelist 字樣與帳號標籤格式即觸發，可能把原本想問「API 白名單」但忘了講 API 的訊息也導向後台流程。 若訊息完全沒有可解析的帳號，仍會安全失敗（記錄 log、不回覆），不會亂猜；但若群組同時開啟「單一總代理模式」，請參考上方「與寬鬆觸發規則疊加的風險」說明。

AI機器人救援（運作細節）

設定入口見 機器人管理頁面 → AI機器人救援 Tab，這裡說明背景真正如何運作。

設計目的 當某個群組把「AI 問答」關掉、改由真人客服負責時，若真人一時忙碌沒有即時回覆，AI 救援可以在「等待一段時間後仍無人回應」的情況下自動接手，避免使用者被晾在一邊太久。

背景排程

系統啟動時會啟動一個永久迴圈，每 60 秒掃描一次所有「已啟用救援」的機器人。

1
收集候選訊息
只有當某群組的「AI 問答」關閉時，該群組收到的非引用回覆訊息才會被記錄為「救援候選」；若使用者訊息是直接引用（reply）某則候選訊息，代表已被真人處理，該候選會被標記為「已處理」，不會再被救援。
2
逾時篩選
每輪掃描找出「建立時間已超過設定的逾時分鐘數、且尚未處理」的候選訊息；同一群組若有多則，只取最新一則處理，其餘舊候選一併標記為已處理（不會逐則都救援）。
3
AI 判斷是否為「問題」
呼叫 Claude Haiku 只回答 yes/no，排除單純問候、感謝、簡短回應（例如「謝謝」「你好」「OK」「收到」）等不需要回答的訊息，避免對這類訊息也強行回覆。
4
查詢知識庫並回覆
與一般流程相同的知識庫查詢邏輯；有答案就回答案，沒有答案則發送制式等待訊息（依語言自動切換）。回覆時會引用原始訊息，讓使用者清楚知道是回覆哪一則。
限制條件
掃描頻率每 60 秒一輪，因此實際觸發時間點與設定的「逾時分鐘」相比會有最多 1 分鐘誤差
逾時可調範圍1 ～ 1440 分鐘（1 分鐘 ～ 24 小時）
前提條件該機器人啟用中 且 該機器人啟用救援 且 該群組 AI 問答已關閉
每群組每輪只救援最新一則候選，避免一次回覆一長串堆積的舊訊息
不受管控模式影響AI 救援的回覆是直接呼叫 Telegram API 送出，不會進入「待發送回覆」審核佇列
